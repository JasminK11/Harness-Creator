Das Problem, das das Projekt löst

Ohne Bibliothek

  • Agenten-Setups werden immer wieder neu erfunden
  • Gutes Material verstreut in hunderten fremden Repos
  • Niemand weiß, wann ein Skill, Hook oder Subagent richtig ist

Die Falle beim Sammeln

  • Der volle Katalog umfasst rund 20 MB JSON
  • Wer ihn einliest, hat sein Kontextfenster voll, bevor er die erste Zeile Projektcode sieht
  • Deshalb: Zugriff nur über ein eigenes CLI
# Die bindende Zugriffsregel
node tools/harness.mjs search "<stichwort>"   # finden
node tools/harness.mjs show <id>              # prüfen
node tools/harness.mjs install <id> --to .    # einbauen

Architektur: vier Schichten

1 · Quellen — sources.txt: 14 Repos mit Vertrauenszeile (offiziell / gepflegt / unbekannt). Klone liegen außerhalb des Projekts.
2 · Katalog — catalog/index.json (~20 MB) plus dreistufiger Index: INDEX.md (immer lesbar) → by-domain/*.md → Vollindex (nie lesen).
3 · Werkzeug — tools/harness.mjs: ~15 Subcommands, nur Node-Standardbibliothek, keine Abhängigkeiten. Einziger Zugriffsweg.
4 · Wissen — knowledge/ (8 Dateien, begründetes Wissen), recipes/ (6 Baupläne je Projekttyp), Learnings/ (Rohquellen, nur lesen).

Jede Aussage trägt ihren Beleg. Nichts kommt aus dem Modellgedächtnis. lint prüft Zahlen, IDs und die Nähte zwischen Text und Maschine.

Qualitätssicherung: drei Schranken

lint — hält Text gegen Text und Text gegen Maschine: veraltete Bestandszahlen, tote Baustein-IDs, CLI-Aufrufe gegen den Dispatcher, Nahtprüfung über alle Markdown-Dateien inklusive .claude/. Aktuell: 0 Befunde.
eval — misst die Suche gegen 13 Pflichtfälle in evals/routing.jsonl; meldet Rangverschiebungen, bevor ein Fall durchfällt. Läuft als Schritt 4 jedes update.
Adversarialer Prüfer — separater Subagent mit der Standardhaltung „ablehnen". Er sieht das Ergebnis, nicht die Begründung. Grund: Ein Agent, der seine eigene Arbeit bewertet, findet sie gut — messbar.

Nutzung in einem Zielprojekt

cd /pfad/zum/zielprojekt

# Was brauche ich? Erst list, dann search/intent, dann show, dann install
node <bibliothek>/tools/harness.mjs list --to .
node <bibliothek>/tools/harness.mjs intent --list        # Symptom statt Suchwort?
node <bibliothek>/tools/harness.mjs search "react testing" --limit 5
node <bibliothek>/tools/harness.mjs show affaan-m__ecc/skill/react-testing
node <bibliothek>/tools/harness.mjs install <id...> --to . --yes
  • install meldet danach, was [aktiv] wirkt und was [inaktiv] bleibt (Hooks brauchen settings.json, MCP braucht Zugangsdaten)
  • Kollisionen brechen den Lauf ab — kein stilles Mischen zweier Autoren
  • Jedes Zielprojekt bekommt ein Manifest (.claude/harness-manifest.json) als Herkunftsnachweis

Tiefbau 1: Wie der Katalog entsteht

sync
git clone / pull je Zeile in sources.txt → ~/.harness-sources
→
extract
läuft über jeden Klon: SKILL.md, agents/, commands/, hooks/, .claude/
→
Katalog
index.json + by-domain/*.md + INDEX.md + Hygiene-Zahlen ins CHANGELOG
→
eval
13 Pflichtfälle müssen die Suche noch finden, was sie finden soll

Hygiene-Kennzahlen bei jedem extract

  • Bausteine ohne brauchbare Description → Quarantäne (nur mit --quarantine sichtbar)
  • Bausteine in mehr als 3 Domänen, Anteil in der Auffang-Domäne general
  • Namensdubletten über Repos — nur berichten

Alles deterministisch, kein LLM im Bau — der Katalog ist nachvollziehbar reproduzierbar.

Tiefbau 2: Wie die Suche funktioniert

  • Wortanfangs-Matching mit Flexions-Streifung: pruefen und pruefung laufen beide auf den Stamm pruef (Endungen ung/ungen/en ab Rest ≥ 4, e ab Rest ≥ 5, kuratierte Ausnahmen wie rechnung)
  • DE-EN-Glossar: 39 kuratierte Fachbegriffspaare — sicherheit prüfen bewertet zusätzlich security review
  • UND-Suche mit ODER-Fallback: trägt kein Baustein alle Wörter, fällt die Suche auf Teiltreffer zurück — und sagt das
  • Absichts-Ebene (intent): 13 kuratierte Absichten mit Anker-Bausteinen für Symptom-Fragen ohne Suchwort
  • Kleinheitsbonus: was beim Greifen wenig Kontext lädt, gewinnt bei Gleichstand
  • Evals als Netz: 13 Pflichtfälle fangen jede Score-Änderung ab, bevor sie still schlechter macht

Kein Embedding, keine Vektordatenbank, kein LLM — absichtlich: deterministisch, debuggbar, kostenlos.

Tiefbau 3: Was install wirklich tut

node tools/harness.mjs install <id...> --to <projekt>
  • Vor dem Kopieren: Sicherheits-Sichtung — welche Dateien sind ausführbar, wo stehen Prozess-/Netzwerk-Aufrufe (Fundstelle mit Zeilennummer)
  • Kollisionen brechen ab: zwei Bausteine auf denselben Pfad = ganzer Lauf bricht ab, auch mit --force — kein Mischbestand zweier Autoren
  • Manifest: .claude/harness-manifest.json — je Eintrag Typ, Quelle, Repo-Head, Dateipfade + md5-Prüfsummen, Installationsdatum
  • Zustandsbericht danach: [aktiv] wirkt sofort · [inaktiv] braucht einen Schritt von Hand (Hook-Registrierung, MCP-Zugangsdaten) — kopiert heißt nicht wirksam
  • uninstall entfernt nur Manifest-Dateien: lokal angepasste Kopien bleiben ohne --force stehen

Lifecycle: Wer hält meinen Harness aktuell?

Die Frage: Neue Bausteine kommen täglich, Repos ändern sich — wer sagt mir, dass mein installiertes Setup veraltet ist? Antwort: der Subcommand check.

node tools/harness.mjs check --to <projekt>

[aktuell]  affaan-m__ecc/skill/react-testing
[geändert] affaan-m__ecc/agent/code-reviewer
           installiert @ a1b2c3d, Katalog-Head @ d8409a4 — das Repo hat sich
           bewegt; ob DIESER Baustein es tat, sagt `show`
[entfernt] alt__repo/skill/weg
Bilanz: 1 aktuell, 1 geändert, 1 entfernt, 0 mit Brüchen.
ZustandBedeutungExit-Code
[aktuell]Repo-Head unverändert, Dateien intakt1 nur bei echten Brüchen (entfernte IDs, fehlende Dateien) — CI-tauglich
[geändert]Repo-Head wanderte; show klärt ob gerade dieser Baustein
[entfernt]ID aus dem Katalog verschwunden (upstream gelöscht/umbenannt)

Der Workflow: nach jedem Bibliotheks-update einmal check --to <projekt> — oder als CI-Schranke per Exit-Code.

Tiefbau 4: Wissensbank-Interna

  • OKF-Frontmatter je Datei: sources, status, stale_after, generated — verified nur nach menschlicher Lesung
  • Abschnitt = Liefereinheit: Überschriften sind Suchtreffer; knowledge "<frage>" schneidet den passenden Abschnitt heraus (325 Abschnitte / 16 Dateien)
  • LOG.md ist append-only: Datum · Aktionsart (add/revise/ingest/werkzeug/lint) · Titel · Begründung · Prüfprotokoll — nie löschen
  • lint-Nähte: jeder CLI-Aufruf in einem Codeblock wird gegen den Dispatcher geprüft, jede Baustein-ID gegen den Katalog, jede Zahl gegen stats — Text kann so nicht still verrotten
  • Zweitbelege statt Dopplungen: findet neues Material nur Bestätigung, wird es als Quellenzeile eingehängt — nicht als neuer Abschnitt (der Fehler M1–M12 darf nie wieder passieren)

Die fünf Regeln, an denen alles hängt

  • Nichts aus dem Gedächtnis ergänzen — jede Zahl per CLI ermitteln
  • Nie index.json oder Klone direkt lesen — nur das CLI
  • Prüfen heißt: von jemand anderem prüfen lassen — mit Ablehnungs-Haltung
  • Einfachste Lösung zuerst — Komplexität nur, wenn ein Problem sie erzwingt
  • Kein Baustein ist besser als ein unpassender — Lücken werden benannt, nicht gestopft

Ein Werkzeug, das seine eigenen Regeln nicht befolgt, ist der beste Beweis, dass die Regeln nichts taugen. Deshalb frisst dieses Projekt seine eigene Dog Food.
